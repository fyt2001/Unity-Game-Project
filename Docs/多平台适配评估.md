# 多平台适配评估与改造清单

> 目标平台：Steam（PC）、Android、iOS、微信小游戏
> 依据：本项目实际代码扫描 + 微信官方《Unity WebGL 微信小游戏适配》能力表
> 状态：评估结论，未改动任何代码

## 一、结论摘要

**Android / iOS / Steam 基本没障碍**；**微信小游戏有 3 个硬伤**，但其中最严重的资源加载问题**已有低成本解法**（框架预留了 provider 注入口）。

最关键的一条建议：**现在就抽平台抽象层**，不要等到适配时到处加 `#if UNITY_WEBGL`。

## 二、平台矩阵

| 平台 | 评估 | 阻塞程度 | 主要工作 |
|---|---|---|---|
| Steam（PC） | 🟢 最省事 | 无 | 原生库齐全；接 Steamworks；确认 Scripting Backend |

## 四、微信小游戏的 3 个硬伤

### 硬伤 1：资源加载方式不兼容（最严重，但最好解决）

**问题**：官方能力表明确——资源加载**只支持 Addressable / AssetBundle 网络异步加载**；代码包总大小 ≤ 20MB、主包 ≤ 4MB（单个分包不限）。

而项目 Lua 侧**只有一个 `ResourcesProvider`**（`Game/LuaScripts/Game/UI/Provider/`）。`Resources/` 目录内容会被**全部打进首包**，既撑爆体积，又无法网络异步加载与热更。

**解法（低成本）**：框架已预留注入口，无需改动框架本身。

- `UIManager` 支持 `options.resourceProvider`
- `UIResourceLoader` 定义的 provider 接口：`LoadAsync / Release / Instantiate / Destroy`（`UIResourceLoader.lua:43-45`）

只需新增 `AssetBundleProvider.lua` 实现这 4 个方法，内部桥接到已有的 C# `AssetBundleManager` 即可整体切换：

```lua
local AssetBundleProvider = {}
function AssetBundleProvider:LoadAsync(path, cb)  -- 桥接 CS.AssetBundleManager
function AssetBundleProvider:Instantiate(asset)
function AssetBundleProvider:DestroyInstance(go)
function AssetBundleProvider:Release(path, asset)
```

### 硬伤 2：文件系统不支持 ✅ 抽象层已抽出（`WeChatStorage` 待接入）

**问题**：官方明确**不支持 `System.File`**，需用 WX SDK 文件存储（限额 200MB，满足条件可申请至 1G）。

命中代码（存档 / 日志 / 配置全部受影响）：

| 文件 | 位置 | 用法 |
|---|---|---|
| `Game/LuaScripts/Game/Save/SaveManager.lua` | 137-163 | `CS.System.IO.File/Directory` 读写存档（`WriteAllText`/`Move`/`Delete`） |
| `Game/Scripts/Utils/FileUtils.cs` | 84, 87, 153, 211 | `Directory.CreateDirectory`、`File.WriteAllBytes` |
| `Game/Scripts/Utils/JsonUtils.cs` | 89, 92 | `Directory.CreateDirectory`、`File.WriteAllText` |
| `Game/Scripts/Debug/DebugLogger.cs` | 32 | `File.WriteAllText` 写日志 |
| `Game/Scripts/Common/VersionFile.cs` | 94 | `File.WriteAllText` |
| `Game/Scripts/Core/GameLaunch.cs` | 229 | `Directory.CreateDirectory(persistentDataPath)` |

**解法**：抽 `IStorage` 抽象（C# + Lua 双侧），微信端走 WX SDK，其它平台走 `System.IO`。

### 硬伤 3：无 `UNITY_WEBGL` 分支 → 触屏操作失效 ✅ **已解决**

**问题**：`Game/Scripts/GameLaunch/HomeSceneBootstrapper.cs:1215` 的移动指令：

```csharp
#if UNITY_ANDROID || UNITY_IOS || UNITY_TVOS
        if (Input.touchCount > 0)          // 触摸分支
#else
        if (Input.GetMouseButtonDown(1))   // 右键分支：下达移动指令
#endif
```

WebGL 不在前者中 → 微信小游戏（触屏设备）会走**鼠标右键**分支，**点按无法下达移动指令**。

**解法**：改为运行时判断 `Input.touchSupported`，比继续加平台宏更稳（同一份代码同时覆盖 PC 与触屏）。

### 另外两个要留意

- **Luajit 不可用**：小游戏"支持 xlua，但不支持 Luajit"，且 iOS 本身也无 JIT。`Battle/` 下 23 个 lua 的每帧战斗逻辑建议尽早做真机性能实测。
- **网络**：不支持 `System.Net`。目前扫描未见 Socket/TCP 用法，HTTP 走 `UnityWebRequest`（`WebRequestLua.cs`）是允许的；若后续加长连接需改用 WebSocket / WX SDK。

## 八、Lua 脚本打包（方案已定：C / AssetBundle）

### 背景：真机 Lua 加载原本是断的

- `Game/Resources/` 下 **0 个** Lua 文件；137 个 `.lua` 在 `Assets/Game/LuaScripts/`。
- `.lua` **不是** Unity 的 TextAsset 扩展名（Unity 只认 `.txt/.json/.bytes/...`，这也是 XLua 官方资源命名为 `util.lua.txt` 的原因）→ `Resources.Load<TextAsset>` 取不到。
- `LuaGameBootstrap.CustomLuaLoader`（`luaEnv.AddLoader` **无条件注册**、无模式开关）走 `Application.dataPath` + File IO → Android 的 `dataPath` 在 APK 内，**必挂**。

**结论：改造前只有 Editor 能跑，Android / iOS / WebGL 打包全断。**

  - `InitLuaEnvCoroutine()` —— **异步，全平台通用**（推荐入口）
  - `SetupLuaEnv()` —— AB 就绪后的公共初始化（建 LuaEnv / AddLoader / buildin / require）
- `GameLaunch.cs` 的启动协程改为 `yield return StartCoroutine(lua.InitLuaEnvCoroutine())`。
  非 WebGL 下 `LoadAsync()` 同帧完成，**行为与改造前一致**；WebGL 下才会真正等待网络拉取。
- 取脚本顺序：`LuaBundleLoader.TryGetScript()` → 取不到回落原 Resources 逻辑，
  因此 AB 未就绪时不会硬失败（零回归）。

### 关键约束（决定了实现方式）

- XLua 的 `CustomLoader` 是**同步**的 → 不能"用到哪个模块再异步加载"，必须**启动阶段把 Lua AB 整体加载好**，之后 loader 从已加载的 bundle 同步取。
- **WebGL / 微信小游戏没有文件系统**，`AssetBundle.LoadFromFile` 不可用 → 必须 `UnityWebRequestAssetBundle`（异步）。
  这也解释了 **H02 为何用 `UnityWebRequest`**：它读的是 `script.asset`，而 Android 的 `streamingAssetsPath` 在 APK 压缩包内，File IO 读不到。
- 因此即使走 C（AB）方案，小游戏端仍然会用到 `UnityWebRequest`。
